## Direct runtime evidence

The retained raw log records the exact crosvm argument generated by `vm run`:

```text
--serial=type=file,path=/proc/self/fd/26 (.../uart-output.bin),
input=/proc/self/fd/27 (.../uart-input-4096.bin),hardware=serial,num=1
```

`uart-input-4096.bin` was the pushed 4,096-byte ordinary file. Thus `fd 27`
was an ordinary file descriptor, not a FIFO, pipe, PTY, or socket. Immediately
after crosvm started, it emitted:

```text
Failed to create wait context. Operation not permitted (os error 1)
```

Source log: `build-logs/shell-serial-loopback-20260907/logcat-runtime-window.txt`
(SHA-256 `1D0CDDCDFA13030C575A15888142D76E7E41BEFFA4DB5938A5CC1161E71B7695`).

## Exact crosvm path

The error string is emitted by crosvm `devices/src/serial.rs`,
`Serial::spawn_input_thread()`. It builds a `WaitContext` containing the serial
RX notifier and the kill event. Current AOSP crosvm sources show this sequence:

```text
--console-in path
  -> SerialParameters::create_serial_device()
  -> open_file_or_duplicate(... read(true)) -> std::fs::File
  -> ReadNotifier for File -> the File descriptor itself
  -> Serial::spawn_input_thread() -> WaitContext::build_with(...)
  -> EventContext::add_for_event() -> epoll_ctl(EPOLL_CTL_ADD, fd, ...)
```

`base/src/sys/linux/poll.rs` is the Linux `WaitContext` implementation. Its
`add_for_event()` calls `epoll_ctl(EPOLL_CTL_ADD)` and returns the Linux errno
unchanged. Since crosvm had already created the context and only the regular
file was added as the RX notifier, the observed `EPERM` identifies the
`epoll_ctl(ADD)` attempt on that regular file. Linux rejects regular files from
an epoll interest set with `EPERM`.

Primary source references:

- [serial.rs](https://android.googlesource.com/platform/external/crosvm/+/refs/heads/main/devices/src/serial.rs)
- [serial_device.rs](https://android.googlesource.com/platform/external/crosvm/+/refs/heads/main/devices/src/serial_device.rs)
- [notifiers.rs](https://android.googlesource.com/platform/external/crosvm/+/refs/heads/main/base/src/notifiers.rs)
- [Linux poll implementation](https://android.googlesource.com/platform/external/crosvm/+/refs/heads/main/base/src/sys/linux/poll.rs)

## Resolved follow-up

The regular-file experiment did prove guest-to-shell startup output, but did
not test a valid crosvm RX notifier. A separately authorized disposable test
then used an inherited anonymous pipe. It passed the complete 4,096-byte
`00..FF` loopback with exact SHA-256 equality; crosvm logged `pipe:[4923896]`
for its serial input and exited normally. Android shell could not create a
named FIFO in `/data/local/tmp`, but that limitation does not affect the
inherited-pipe design.

```text
binary-safe adb/shell writer
  -> inherited anonymous pipe
  -> vm run --console-in <FIFO path>
  -> crosvm serial hardware=serial,num=1
  -> bare-metal UART echo probe
  -> ordinary output capture file
```

Do not use `vm console` or a PTY. The remaining prerequisite is not serial
transport but a separately approved diagnostic Windows clone and a minimal,
reversible BCD bootdebug configuration. Full runtime evidence:
`docs/SHELL_SERIAL_PIPE_LOOPBACK_RUNTIME_2026-09-07.md`.
